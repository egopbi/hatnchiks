## 1) Паспорт проекта

* **Название проекта:** Hatnchiks
* **Техстек (языки/фреймворки):** Python 3.12, FastAPI, Pydantic, SQLAlchemy, Redis, PostgreSQL, FastAPI Users, Uvicorn, Loguru
* **Цель репозитория (1–2 предложения):** Асинхронный backend для игры «Шляпа»: управление пользователями, карточками, играми и игровыми раундами через REST API.
* **Критерий успеха изменений (DoD — Definition of Done):**

  * Изменения удовлетворяют описанным ниже правилам безопасности и качества.
  * Все проверки `uv run pytest -q` проходят локально и в CI.
  * Тесты добавлены/обновлены, покрытие не снижается (или ≥ 80%).
  * Документация и примеры кода обновлены.

## 2) Роли и режимы работы агента

* **Режимы:**

  1. **Чтение/Анализ (READ-ONLY):** поиск, индексация, построение плана, извлечение фактов.
  2. **Изменение (WRITE):** строго детерминированное внесение правок по плану и чек-листам.
* **Обязательная последовательность:** `READ-ONLY → План → Подтверждение внутренних инвариантов → WRITE → Самопроверка → Формирование коммита/PR`.

## 3) Жёсткие правила безопасности

### 3.1 Доступ к файлам

* **Разрешено:** читать и редактировать **только** файлы, которые **не** совпадают ни с одним паттерном из `.gitignore`.
* **Запрещено:**

  * Любые операции над файлами/папками, подпадающими под `.gitignore` (включая скрытые артефакты, кэши, секреты, локальные конфиги).
  * Создание новых файлов в путях, игнорируемых `.gitignore`.
* **Алгоритм проверки пути перед записью:**

  1. Прочитать `.gitignore` и вычислить итоговый набор паттернов.
  2. Для каждого изменяемого пути выполнить сопоставление с паттернами (как делает `git check-ignore`).
  3. Если путь игнорируется — **отклонить изменение** и зафиксировать в отчёте причину.

### 3.2 Секреты и персональные данные

* Никогда не читать/писать значения переменных окружения, секретов, токенов.
* Не добавлять секреты в код/конфиги/логи/коммиты/PR-описания.
* При обнаружении секрета — **остановить изменения**, создать задачу: *“Обнаружен секрет в <path-to-secret>: требуется ротация и удаление из истории”*.

### 3.3 Исполнение кода и сеть

* **Не запускать** произвольный код и команды, кроме оговорённых в разделе «Инструменты».
* **Не обращаться** в интернет (скачивание зависимостей допускается **только** через описанные команды и lock-файлы).
* Любые генерации данных/миграций, меняющих прод-состояние, — **запрещены** без явного чек-листа и флага `ALLOW_MIGRATIONS=false`.

## 4) Область задач (Scope) и приоритеты

* **Приоритет A (обязательные):** исправление компиляции/линта/тестов; критические баги; безопасность.
* **Приоритет B (желательные):** локальные рефакторинги без изменения публичных контрактов.

## 5) Формат входного задания (Task Spec)

Агент ожидает входные данные в JSON (или YAML) с полями:

```json
{
  "id": "TASK-123",
  "title": "Fix hat round overflow",
  "goal": "Игроки не должны тянуть карточки после третьего раунда.",
  "acceptance_criteria": [
    "при переходе в четвёртый раунд API возвращает 400 и сообщение об окончании игры",
    "pytest tests/test_api/test_games.py::TestAPIGames::test_post_create_game проходит"
  ],
  "change_type": "bugfix|feature|refactor|docs|chore",
  "constraints": [
    "Нельзя менять публичные API в пакете src.backend",
    "Сохранить обратную совместимость с Python 3.12"
  ],
  "affected_paths": ["src/backend/**", "tests/test_api/**"],
  "forbidden_paths": ["generated/**", "scripts/local/**"],
  "examples": {
    "input": "POST /games/{game_id}/cards {\"user_id\": \"user-1\", \"text\": \"Шерлок Холмс\"}",
    "output": "{\"success\": true, \"message\": \"Card 'card-xxxxx' was added\"}"
  }
}
```

**Пример заполнения:**

* `goal`: “Сделать функцию `parse_user()` устойчивой к отсутствию поля `email`”.
* `acceptance_criteria`: “Не падать на `None`, вернуть `Optional[str]`”.
* `constraints`: “Не менять сигнатуру внешнего метода `UserService.get()`”.

## 6) Планирование изменений (детерминированный алгоритм)

1. **Индексировать кодовую базу** в разрешённых путях; собрать карту модулей/зависимостей.
2. **Выделить минимальный срез изменений**, достаточный для критериев принятия (минимальный дифф).
3. **Согласовать инварианты качества** (см. раздел 8).
4. **Сформировать пошаговый план**:

   * Файл/участок → Изменение → Причина → Риск/откат.
5. **Проверка против `.gitignore`** каждого шага.
6. **Применить изменения строго по плану.**
7. **Запустить проверки:** форматтер, линтеры, сборка, тесты.
8. **Самоаудит диффа** по чек-листам (см. разделы 8–12).
9. **Сформировать коммит/PR** по шаблонам (раздел 11).

---

## 7) Политика «Границы редактирования»

* Меняем **только** те строки, которые необходимы для выполнения цели.
* Не перемещаем большие блоки кода без нужды.
* Не переименовываем публичные символы без явного требования.
* Комментарии/докстринги добавляем **рядом** с изменённым кодом; не переписываем существующие без причины.
* При сомнении: предпочитаем **локальный патч** вместо широкого рефакторинга.

## 8) Качество кода — инварианты

* **Статический анализ:** `uv run ruff check` без ошибок.
* **Форматирование:** `uv run ruff format` (например, `ruff format`/`black`/`prettier`) обязателен.
* **Типы:** если проект типизирован — исправлять предупреждения типов (`mypy`, `pyright`, `tsc`).
* **Архитектура:** не нарушать слои (`domain → application → infra`), зависимости, направленные «вверх → вниз», запрещены.
* **Именование:** следовать стилю проекта (PEP 8/Google/Airbnb/etc.).
* **Логирование и ошибки:** использовать принятые уровни (`DEBUG/INFO/WARN/ERROR`), не глушить исключения.

---

## 9) Тесты

* **Где размещать:** рядом с кодом или в `tests/` по принятому в проекте паттерну.
* **Что покрывать:** новые ветви, граничные случаи, регресс ошибки.
* **Шаблон тест-кейса (пример, Python/pytest):**

  ```py
  def test_parse_user_without_email_returns_none():
      user = {"name": "Ann"}
      assert parse_user(user).email is None
  ```
* **Команда запуска:** `uv run pytest -q` (пример: `pytest -q`).
* **Политика snapshot-тестов:** изменился снапшот → приложить причину в PR-описание.

## 10) Зависимости и миграции

* **Добавление/обновление зависимостей:** только с lock-файлом (`uv.lock`), версия фиксируется (`~=`/`^` согласно политике).
* **Миграции БД/схем:** запрещены по умолчанию. Если `ALLOW_MIGRATIONS=true`:

  * Миграции атомарные, обратимые; отдельным коммитом.
  * Шаблон: `alembic generate "reason"` → `apply` только в CI job `migrations-verify`, не в основном пайплайне.

## 14) Политика работы с текстом и кодом (детализация патчей)

* **Мелкие патчи:** правка конкретных строк (≤ 20) — один коммит.
* **Средние:** логически связанные изменения (≤ 200) — разбить на 2–3 коммита по слоям.
* **Крупные:** запрещены без отдельной задачи и плана миграции.
* **Порядок изменений в файле:** импорты → константы → типы/интерфейсы → функции → классы → экспорт.
