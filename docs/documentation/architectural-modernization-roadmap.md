# Дорожная карта архитектурной модернизации Hatnchiks

## 1. Контекст и текущее состояние
- **Домен продукта**: Асинхронный бэкенд для пати-игры «Шляпа»; управляет пользователями, игровыми сессиями, раундами, карточками и подсчётом очков.
- **Текущая архитектура**: Монолитный сервис FastAPI с пересечением ответственности (API, бизнес-логика, персистентность, интеграции) в каталоге `src/`. Бизнес-потоки сильно завязаны на репозитории Redis, при этом использование реляционной БД находится на ранней стадии.
- **Предпосылки развёртывания**: API на Uvicorn, однопроцессный режим, инфраструктура Redis + PostgreSQL, полностью асинхронный стек.
- **Ключевые наблюдения**  
  - Сквозные задачи (логирование, аутентификация, доступ к данным) реализованы частично и без цельных абстракций.  
  - Доменная логика размазана между обработчиками API и Redis-репозиториями (`GameService`, `HatService`).  
  - Персистентность сосредоточена в Redis; интеграция с Postgres не завершена (модели SQLAlchemy есть, но практически не используются).  
  - Управление зависимостями и жёсткая привязка к настройкам (например, прямое чтение `settings`) мешают тестированию.  
  - Покрытие автоматизированными тестами минимально; взаимодействие слоёв не проверено.  
  - Отсутствуют чёткие инструкции по масштабированию на несколько инстансов (идемпотентность, блокировки, обработка событий).  
  - Документация содержит тактические заметки вместо архитектурных правил работы.

## 2. Цели модернизации
1. **Построить слоистую архитектуру**, разделив уровни API, прикладных сервисов, доменной логики, инфраструктуры и интерфейсов.  
2. **Усилить модель хранения**, добавив реляционную «опорную» БД для устойчивых сущностей при сохранении Redis для эфемерного состояния.  
3. **Формализовать домен игры** с явными агрегатами (Game, Hat, Round, Team, PlayerCard) и конечными автоматами.  
4. **Унифицировать аутентификацию и авторизацию** в духе FastAPI Users: ротация токенов, проверки прав.  
5. **Повысить операционность и устойчивость** (логирование, трассировка, health-check, фоновые задачи).  
6. **Сделать процесс разработки зрелым**: полноценные тесты, статический анализ, линтеры, документация.  
7. **Подготовить горизонтальное масштабирование** за счёт статeless-ноды API и абстрагированных адаптеров инфраструктуры.  
8. **Обеспечить безопасность изменений** через стратегию миграций, поэтапную поставку и явные гарантии совместимости.

## 3. Принципы и ограничения
- **Пошаговая эволюция**: никаких «выбросить и переписать». Новые структуры внедряем рядом с легаси и мигрируем постепенно.  
- **Дизайн вокруг домена**: логика игры описывается явно; технические слои обслуживают эти абстракции.  
- **Async-принцип**: сохраняем асинхронную семантику, добиваемся согласованности ресурсов (сессии БД, Redis, фоновые задачи).  
- **Стабильность контрактов**: публичные HTTP API остаются обратимо совместимыми, если не договоримся о версионировании.  
- **Наблюдаемость по умолчанию**: метрики, логи и трассировки — часть стандартного поведения сервиса.  
- **Безопасность**: секреты изолированы, минимальные привилегии, усиленная обработка токенов.  
- **Синхронность документации и тестов**: каждое архитектурное изменение сопровождается документацией и регрессионными тестами.  
- **Готовность к эксплуатации**: автоматизация миграций, сидов, создания суперпользователя и smoke-тестов обязательна до релиза.

## 4. План рефакторинга домена и слоёв

### Фаза 4.1: Определение границ домена и общего языка
1. **Инвентаризация моделей**  
   - Подготовить контекстные карты для субдоменов: *Lobby Management*, *Card Submission*, *Round Execution*, *Scoring/Leaderboard*, *User Management*.  
   - Выделить корневые агрегаты и инварианты: `Game`, `Hat`, `Player`, `Team`, `Card`, `Round`.
2. **Скелет доменного слоя**  
   - Создать модули `src/domain/<bounded_context>/` с сущностями, объектами-значениями, событиями и сервисами.  
   - Перенести ключевую логику (например, вытягивание карточки, переход раунда) в чистые доменные сервисы с явными входами/выходами.
3. **Контракты слоя приложений**  
   - Ввести оркестраторы в `src/application/`, связывающие доменные операции и инфраструктуру.  
   - Определить use-case: `CreateGame`, `StartRound`, `PullCard`, `RegisterUser` и т.д. с DTO команд и ответов.
4. **План миграций**  
   - Обернуть существующие обработчики API адаптерами, вызывающими новые прикладные сервисы.  
   - Сохранить тесты на равенство поведения старой и новой реализации на время переходного периода.

### Фаза 4.2: Разделение инфраструктуры и персистентности
1. **Интерфейсы репозиториев**  
   - Формализовать протоколы в `src/domain/ports/` для `GameRepository`, `UserRepository`, `SessionRepository`.  
   - Отразить текущие реализации Redis и SQLAlchemy в адаптерах `src/infra/redis` и `src/infra/postgres`.
2. **Паттерн Unit of Work**  
   - Ввести асинхронные UoW-абстракции для координации транзакций (Postgres) и согласованности между хранилищами.
3. **Моделирование данных**  
   - Расширить модели SQLAlchemy на все устойчивые сущности (игры, раунды, команды, очки).  
   - Спроектировать миграции (Alembic) для эволюции схемы, соблюдая `settings.db.naming_conventions`.
4. **Политика кеширования**  
   - Определить роль Redis (эфемерное состояние шляпы, активные игры, rate limiting).  
   - Настроить сброс кеша и прогрев, связывая с доменными событиями.

### Фаза 4.3: Перестройка слоя API
1. **Реструктуризация роутеров**  
   - Группировать маршруты по контекстам (`users`, `games`, `rounds`, `cards`, `admin`).  
   - Стандартизировать обёртки ответов, обработку ошибок и статусы.  
   - Применить ответные модели Pydantic, согласованные с DTO приложений.
2. **Middleware и зависимости**  
   - Централизовать связывание зависимостей в `src/interface/http/dependencies.py`.  
   - Заменить глобальные синглтоны на сервисы, внедряемые через зависимости с областью запроса.
3. **Валидация и безопасность**  
   - Перенести проверку запросов (схемы, бизнес-правила) в прикладной слой.  
   - Встроить RBAC/пермишены через FastAPI Users и доменные политики.
4. **Стратегия версионирования API**  
   - Ввести пространство `/api/v1`. Зафиксировать график депрекации легаси-эндпоинтов.

### Фаза 4.4: Фоновые процессы и real-time
1. **Игровой цикл**  
   - Оценить асинхронные фоновые задачи (например, отсчёт таймера) через FastAPI `BackgroundTasks` или Celery/Arq.  
   - Гарантировать идемпотентность и устойчивость к ретраям.
2. **Реальное время**  
   - Рассмотреть WebSocket-слой для трансляции раундов и счёта.  
   - При необходимости отделить управление соединениями от доменной логики.

## 5. Сквозные улучшения

### 5.1 Конфигурация и секреты
- Использовать контексты `pydantic-settings` по окружениям (`dev`, `test`, `prod`) с переопределением через переменные среды.  
- Вынести секреты в совместимые с vault хранилища; подготовить процедуру ротации.  
- Добавить валидаторы конфигурации, проверяющие наличие ключей и строк подключения при старте.

### 5.2 Аутентификация и авторизация
- Упорядочить FastAPI Users: собрать `UserManager`, `auth_backend`, роутеры и зависимости в единую схему.  
- Ввести политики паролей, блокировки и стратегию refresh-токенов.  
- Настроить аудит логов для событий аутентификации (логин, сброс, выдача токена).  
- Сформировать матрицу ролей (админ, ведущий, игрок) и применять в прикладных сервисах.

### 5.3 Наблюдаемость и диагностика
- Стандартизировать логирование через struct-log или loguru с режимом JSON; настраивать sink по окружениям.  
- Инструментировать приложение OpenTelemetry (middleware FastAPI, SQLAlchemy, Redis).  
- Предоставить эндпоинты `/health`, `/readiness`, `/metrics` (Prometheus-совместимые).

### 5.4 Обработка ошибок и устойчивость
- Заменить пользовательские исключения с возвратом `False` на типизированные ошибки и согласованные HTTP-ответы.  
- Пробросить доменные исключения в контракты API через перехватчики/ middleware.  
- Определить стратегию ретраев (экспоненциальная задержка) для временных ошибок Redis/БД.  
- Добавить circuit breaker или fallback-паттерны при появлении внешних интеграций.

### 5.5 Перезапуск стратегии тестирования
- Пирамида тестов: модульные (домен), интеграционные (репозитории), контрактные (API), end-to-end (ключевые сценарии).  
- Ввести фикстуры изолированных Redis/Postgres (например, `pytest-asyncio` + Docker Compose).  
- Добить регрессионные тесты существующего поведения API до начала рефакторинга.  
- Добавить мутационное или property-based тестирование для случайных механик (вытягивание карточек, смена раундов).

### 5.6 Инструменты и разработческая среда
- Соблюдать форматирование (ruff, black), статическую типизацию (mypy), безопасность (bandit).  
- Настроить pre-commit и конвейер GitHub Actions (линт, тесты, покрытие, security scan).  
- Задокументировать онбординг: процессы `uv`/`poetry`, настройка окружения, сид-скрипты.  
- Подготовить шаблоны ADR (Architecture Decision Record) для ключевых решений.

## 6. План миграций и поставки

### Фаза 6.1: Фундамент (1–2 недели)
- Создать ADR с целями модернизации, схемой слоёв и выбором технологий.  
- Подготовить новую структуру пакетов (`domain`, `application`, `infra`, `interface`).  
- Внедрить линтеры, форматтеры, конфигурацию типизации; обеспечить зеленый CI.  
- Написать базовую архитектурную документацию со ссылкой на эту дорожную карту.

### Фаза 6.2: Согласование домена и персистентности (3–6 недели)
- Реализовать доменные модели и ключевые use-case (`CreateGame`, `StartGame`, `PullCard`).  
- Предоставить абстракции репозиториев с переходными адаптерами Redis и целевыми Postgres.  
- Перевести пилотный поток (создание игры) на новый стек; включить двойную запись (Redis + Postgres) для проверки.  
- Разработать скрипты миграций и наполнения данных; предусмотреть откат.

### Фаза 6.3: Рефакторинг API и паритет возможностей (7–10 недели)
- Переписать API поверх прикладных сервисов, сохранив контракты.  
- Добавить версионирование; обозначить вывод из эксплуатации старых обработчиков с логированием трафика.  
- Реализовать расширенные сценарии авторизации (сброс пароля, верификация, управление сессиями).  
- Расширить автоматические тесты новой архитектуры; закрепить пороги покрытия.

### Фаза 6.4: Устойчивость и масштабирование (11–14 недели)
- Ввести фоновых работников (таймеры), обеспечить безопасную конкурентность.  
- Усилить стек наблюдаемости; интегрировать приборные панели и базовые алерты.  
- Провести нагрузочное тестирование; выявить узкие места и оптимизировать инфраструктуру (пулы соединений, кэш).  
- Финализировать стратегию blue/green и провести репетицию.

### Фаза 6.5: Переключение и зачистка (15–16 недели)
- Переключить основную персистентность на Postgres, оставив Redis для эфемерного состояния.  
- Удалить устаревшие ветви кода после окна мониторинга и достижения метрик успеха.  
- Архивировать ADR по модернизации с выводами; обновить руководство разработчика.  
- Спланировать следующий цикл (например, аналитика, турнирный режим, матчмейкинг).

## 7. Управление рисками и меры защиты
- **Согласованность данных**: добавить страховки (транзакции, пессимистические блокировки) в период двойной записи.  
- **Сохранение паритета**: поддерживать регрессионный набор для выявления дрейфа поведения; логировать расхождения.  
- **Операционная нагрузка**: выкатывать поэтапно на стейджинг, использовать canary-релизы.  
- **Онбординг команды**: провести воркшопы по новой архитектуре, код-стайлу и доменной модели.  
- **Соответствие безопасности**: после рефакторинга провести threat modeling и свериться с OWASP ASVS.
