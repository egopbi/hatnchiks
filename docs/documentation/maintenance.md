# Ведение документации и примеров

## 1. Обязанность обновлять документацию

Обновлять `README.md`, `CHANGELOG.md` и файлы в `docs/**` при **любом** изменении публичного поведения: API, схем, конфигурации, CLI, миграций.

## 2. Примеры кода

* Примеры должны быть **исполняемыми** и **минимальными** (минимум зависимостей, воспроизводимость).
* Добавляйте раздел «Как запустить» с указанием требуемых команд и окружения.
* Для REST-примеров указывайте эталонные запросы/ответы и коды HTTP.

## 3. Маркировка ломающих изменений

* В `CHANGELOG.md` ломающие изменения помечаются префиксом `BREAKING:` и кратким описанием сути ломки.
* В описании PR указывать инструкцию по миграции клиента (если применимо).

## 4. Структура `CHANGELOG.md`

Рекомендуемый шаблон на релиз:

```
## [x.y.z] — YYYY-MM-DD
### Added
- ...
### Changed
- ...
### Fixed
- ...
### Removed
- ...
```

## 5. Мини-чек-лист при обновлении документации

* [ ] Описание новой/изменённой функциональности добавлено в `README.md` или соответствующий файл в `docs/**`.
* [ ] Примеры запросов/ответов обновлены и проверены на исполняемость.
* [ ] `CHANGELOG.md` дополнен, ломающие изменения помечены `BREAKING:`.
* [ ] Ссылки в документации валидны, пути и имена файлов актуальны.
* [ ] Если требуются миграции/фича-флаг — это отражено в документации.
