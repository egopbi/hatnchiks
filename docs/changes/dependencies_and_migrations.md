# Зависимости и миграции БД

## 1. Политика управления зависимостями

* **Добавление/обновление** допускается **только** при наличии lock-файла (`uv.lock`).
* **Фиксация версий:** используем `~=`/`^` в соответствии с политикой проекта; не тянем «плавающие» `*`.
* **Проверка безопасности:** запускаем аудит после обновлений (если настроен, например `uv run pip-audit`/эквивалент).
* **Совместимость:** изменения не должны нарушать поддержку **Python 3.12**.
* **Минимальный дифф:** не обновлять транзитивные пакеты без необходимости; избегать массовых апгрейдов «за компанию».

### Рекомендуемый процесс

1. Обосновать необходимость зависимости в задаче (зачем, где используется).
2. Добавить/обновить зависимость и **перегенерировать lock**.
3. Прогнать локально: формат/линт/типы/тесты.
4. Описать изменения в PR: версия, причина, риск/откат.

---

## 2. Политика миграций БД

* Миграции **запрещены по умолчанию**.
* Разрешение только при `ALLOW_MIGRATIONS=true` **и** наличии чек-листа.

### Требования к миграции

* **Атомарность:** одна логическая миграция ≙ один файл миграции.
* **Обратимость:** каждая миграция должна иметь корректный `downgrade`.
* **Изолированный коммит:** миграции — отдельный коммит/PR от прикладного кода.
* **Изолированная проверка:** выполняются в отдельной CI-job (например, `migrations-verify`), а не в основном пайплайне.
* **Идемпотентные скрипты:** миграции должны безопасно выполняться повторно (если инструмент это поддерживает).

### Рекомендуемый процесс (пример с Alembic)

1. Создать ветку задачи и включить флаг `ALLOW_MIGRATIONS=true`.
2. Сгенерировать миграцию:

   ```bash
   alembic revision -m "reason"
   ```
3. Заполнить `upgrade()`/`downgrade()` **вручную**, избегая необратимых операций.
4. Локально проверить миграцию на чистой и «грязной» БД.
5. Запушить отдельным коммитом, дождаться прохождения `migrations-verify`.
6. В PR приложить: описание изменений схемы, риски, план отката, инструкции по кат-оффу.

---

## 3. Чек-лист перед PR

* [ ] Lock-файл обновлён и добавлен в коммит.
* [ ] Сборка/линт/типы/тесты — зелёные.
* [ ] Для миграции: атомарность, обратимость, отдельный коммит, отдельная CI-job.
* [ ] Документация обновлена при изменении поведения/схем (ссылка на этот файл).
* [ ] В PR описаны причины, риски и план отката.

---

## 4. Анти-паттерны

* ❌ Массовый апгрейд зависимостей без задачи и обоснования.
* ❌ Миграции в том же коммите, что и логика приложения.
* ❌ Необратимые `DROP` без `downgrade` и без плана восстановления.
* ❌ Скрытое добавление зависимостей через импорт без фиксации в манифесте.
* ❌ Тянуть зависимости из нестабильных источников/без хеша/без lock.
