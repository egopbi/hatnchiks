# Правила разрешения неоднозначностей

## 1. Принципы выбора трактовки

1. **Минимальные изменения публичных контрактов**
   Если задача допускает несколько трактовок, выбирать ту, что не меняет публичные API/схемы/поведение клиентов.

2. **Сохранение обратной совместимости**
   Предпочитать решения, не ломающие существующих пользователей и интеграции.

3. **Фича-флаги для рискованных изменений**
   Новое/экспериментальное поведение помещать под флаг
   `ENABLE_HAT_EXPERIMENTAL_FLOW=false` по умолчанию.

4. **Минимальный дифф**
   Вносить только те изменения, которые напрямую нужны для достижения цели.

5. **Прозрачные допущения**
   Все предположения и ограничения фиксировать в PR (раздел «Почему так»).

---

## 2. Процедура при обнаружении неоднозначности

1. Сформулировать **варианты интерпретаций** (кратко, 1–2 строки каждый).
2. Оценить влияние на **публичные контракты** и совместимость.
3. Выбрать вариант с **минимумом рисков** (см. §1).
4. Если риск средний/высокий — обернуть в **фича-флаг**.
5. Зафиксировать в PR: выбранную трактовку, альтернативы, причины отказа.

---

## 3. Шаблон блока в PR («Почему так»)

```
### Почему так
- Выбрана трактовка: <кратко>
- Альтернативы: <вариант A> / <вариант B> (отклонены, потому что …)
- Совместимость: публичные контракты не менялись | изменились (фича-флаг ENABLE_HAT_EXPERIMENTAL_FLOW)
- Риски и смягчения: <риск>, <как снижен>, <план отката>
```

---

## 4. Когда останавливаем работу и эскалируем

Остановиться и запросить уточнение (или оформить STOP-отчёт), если:

* Возможные трактовки **противоречат** требованиям безопасности/лицензии.
* Любой вариант ведёт к **ломающим изменениям** без возможности фича-флага.
* Налицо **конфликт критериев приёмки** или они взаимоисключающие.

В этом случае оформить `reports/STOP-YYYYMMDD-HHMMSS.md` с описанием вариантов и причин остановки, без формирования коммита/PR.
