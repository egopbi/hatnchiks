# Hatnchiks — Agents.md (Project Rules)

## 1. Назначение файла

Жёсткие правила и порядок работы для любого автоматизированного агента, вносящего изменения в репозиторий Hatnchiks. Всё остальное — в проектной документации.

---

## 2. Режимы и обязательная последовательность

**Режимы:**

1. **READ-ONLY** — поиск, индексация, выделение фактов, построение плана.
2. **WRITE** — детерминированное применение согласованного плана.

**Последовательность (обязательна):**
`READ-ONLY → План → Подтверждение инвариантов → WRITE → Самопроверка → Коммит/PR`.

---

## 3. Жёсткие правила безопасности

### 3.1 Файлы и пути

* Разрешено изменять **только** пути, не попадающие под `.gitignore`.
* Любые операции с игнорируемыми путями **запрещены** (включая создание новых файлов).
* Перед записью: прочитать `.gitignore`, сопоставить путь (аналог `git check-ignore`). Если путь игнорируется — **отклонить** изменение и зафиксировать причину.

### 3.2 Секреты и ПДн

* Не читать/писать секреты, токены, переменные окружения.
* Не добавлять секреты в код/конфиги/логи/коммиты/PR.
* При обнаружении секрета: **остановка**, создать задачу “Обнаружен секрет в <path>: требуется ротация и удаление из истории”.

### 3.3 Исполнение кода и сеть

* Не запускать произвольные команды вне оговорённых инструментов.
* Не обращаться в интернет, кроме установки зависимостей строго по lock-файлам.
* Любые миграции/операции, меняющие прод-состояние, **запрещены** без явного разрешения (`ALLOW_MIGRATIONS=true`) и чек-листа.

---

## 4. Scope и приоритеты

* **A (обязательно):** сборка/линт/тесты, критические баги, безопасность.
* **B (желательно):** локальные рефакторинги без изменения публичных контрактов.
* **C (опционально):** форматирование/комментарии/мелкий DX.
  Расширять Scope **нельзя** без явного требования в задаче.

---

## 5. Входное задание (Task Spec)

Агент принимает JSON/YAML с полями минимум: `id`, `title`, `goal`, `acceptance_criteria[]`, `change_type`, `constraints[]`, `affected_paths[]`, `forbidden_paths[]`.
Если критерии/ограничения не заданы — агент **запрашивает/фиксирует** допущения и минимизирует дифф.

---

## 6. План и применение изменений (детерминированно)

1. Индексировать код в разрешённых путях.
2. Выделить **минимальный** дифф для выполнения критериев.
3. Подтвердить инварианты качества (см. §7).
4. Сформировать пошаговый план: *файл/участок → изменение → причина → риск/откат*.
5. Проверить каждый шаг на соответствие `.gitignore`.
6. Применить изменения строго по плану.
7. Запустить форматтер/линтеры/типы/тесты.
8. Самоаудит диффа по чек-листам.
9. Сформировать коммит/PR.

---

## 7. Инварианты качества

* **Статика:** линт без ошибок.
* **Формат:** форматирование обязательное.
* **Типы:** исправлять предупреждения типизации, если проект типизирован.
* **Архитектура:** не нарушать слои (`domain → application → infra`), зависимостей «вверх» быть не должно.
* **Именование/логи/ошибки:** следовать принятому стилю, не глушить исключения.

---

## 8. Границы редактирования

* Менять **только** необходимое для цели.
* Не перемещать большие блоки без необходимости.
* Не переименовывать публичные символы без явного требования.
* Комментарии/докстринги добавлять рядом с изменённым кодом; не переписывать без причины.

---

## 9. Тесты

* Покрывать новые ветви/границы/регресс.
* Запускать `pytest` в тихом режиме (или эквивалент, принятый в проекте).
* При изменении снапшотов — обосновать в описании PR.

---

## 10. Зависимости и миграции

* Добавлять/обновлять зависимости **только** с lock-файлом; версии фиксировать политикой проекта.
* Миграции БД по умолчанию **запрещены**; при разрешении — атомарны, обратимы, отдельным коммитом и проверяются изолированной job.

---

## 11. Коммиты и PR

* **Conventional Commits** для сообщений.
* В PR указывать задачу, список изменений по файлам, «почему так», риски/откат, чек-лист автора:

  * пути не подпадают под `.gitignore`;
  * формат/линт/типы/тесты пройдены;
  * изменены только необходимые строки;
  * документация обновлена (если нужно).

---

## 12. Разрешение неоднозначностей

1. Выбирать трактовку с **минимальными** изменениями публичных контрактов.
2. Сохранять обратную совместимость.
3. При необходимости — зафичерфлагить (`ENABLE_HAT_EXPERIMENTAL_FLOW=off`).
   Принятые допущения фиксировать в PR.

---

## 13. Запрещённые действия

* Любые изменения путей из `.gitignore`.
* Переписывание истории git.
* Массовые переименования/реформат без задачи.
* Изменения, затрагивающие лицензию/брендинг.
* Интеграции, требующие внешних ключей/сети, без явного разрешения.

---

## 14. Контрольный чек-лист перед коммитом

* [ ] Пути изменений проверены против `.gitignore`.
* [ ] Формат/линт/типы/тесты — зелёные.
* [ ] Тесты добавлены/обновлены.
* [ ] Документация/примеры обновлены (если требуется).
* [ ] Коммит/PR оформлены по правилам.
* [ ] Дифф минимален и локализован.

---

## 15. Эскалация и остановка

При нарушении жёстких правил (секреты, `.gitignore`, миграции без разрешения) — **немедленная остановка** и создание отчёта `reports/STOP-YYYYMMDD-HHMMSS.md` с описанием причины. Коммит/PR **не** формировать.
